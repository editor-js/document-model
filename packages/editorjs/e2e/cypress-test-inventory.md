# Editor.js Cypress Test Inventory with Expected Behavior (source: codex-team/editor.js @ 4ea9eb38)

_Generated by re-reading each Cypress test's actual assertions in the v2 source repo. For every test, the description after the colon states the concrete triggering action and observable outcome, not just the test's English name._

## block-ids.cy.ts

- Block ids
  - Should generate unique block ids for new blocks: Typing into two paragraph blocks and adding a Header block via the toolbox, then calling `editor.save()`, results in every block in the saved output having an `id` of type `string`.
  - should preserve passed ids: Rendering the editor with two blocks that each have an explicit `id` (via `render()`), then calling `editor.save()`, returns blocks whose `id` values match the originally supplied ids in the same order.
  - should preserve passed ids if blocks were added: After rendering two blocks with explicit ids and pressing Enter inside the first block to insert a new block in between (typing "Middle block" into it), `editor.save()` returns data where `blocks[0].id` still equals the first original id and `blocks[2].id` still equals the second original id (the new middle block takes index 1).
  - should be stored at the Block wrapper's data-id attribute: After rendering two blocks with explicit ids, each `div.ce-block` element in the DOM has a `data-id` attribute equal to the corresponding block's id, in order.

## copy-paste.cy.ts

- Copy pasting from Editor
  - pasting
    - should paste plain text: Clicking into the first block and firing a paste event with `text/plain: 'Some plain text'` results in the block's content containing that plain text.
    - should paste inline html data: Pasting a `text/html` payload of `<p><b>Some text</b></p>` into a block results in the block's HTML containing `<b>Some text</b>`.
    - should paste several blocks if plain text contains new lines: Pasting `text/plain` content `'First block\n\nSecond block'` (blank-line-separated) splits it into two separate `div.ce-block` elements whose text contents are `'First block'` and `'Second block'` respectively.
    - should paste several blocks if html contains several paragraphs: Pasting `text/html` `'<p>First block</p><p>Second block</p>'` produces two separate `div.ce-block` elements with text contents `'First block'` and `'Second block'`.
    - should paste using custom data type: Pasting a custom `application/x-editor-js` MIME payload containing a JSON array of two paragraph block descriptors produces two blocks whose text contents match the pasted data (`'First block'`, `'Second block'`).
    - should parse block tags: Pasting `text/html` `'<h2>First block</h2><p>Second block</p>'` (with the Header tool registered) creates an `h2.ce-header` element containing "First block" and a `div.ce-paragraph` containing "Second block"; `editor.save()` confirms `blocks[0]` is type `header` with `data.text === 'First block'` and `data.level === 2`, and `blocks[1]` is type `paragraph` with `data.text === 'Second block'`.
    - should parse pattern: Pasting a bare image URL as `text/plain` (with the Image tool registered) auto-converts the pasted text into an image block, rendering an `img` element whose `src` attribute equals the pasted URL.
    - should not prevent default behaviour if block's paste config equals false: For a custom tool with `pasteConfig = false` whose rendered element has a native `paste` listener, pasting text into that element results in the native paste event handler being called with `defaultPrevented: false` (i.e., Editor.js does not call `preventDefault()` on paste for that block).
  - copying
    - should copy inline fragment: Selecting all text within a single block (via `{selectall}`) and firing a copy event yields empty clipboard data, since Editor.js only intercepts copy for multi-block/cross-block selections and otherwise lets the browser handle it natively.
    - should copy several blocks: After typing into two blocks and selecting from the second block's start up through the first block (Shift+Up), firing copy produces clipboard data where `text/html` matches two `<p>` elements containing "First block" and "Second block", `text/plain` equals `'First block\n\nSecond block'`, and (after a tick, since it's set asynchronously) `application/x-editor-js` is a JSON array of two paragraph-tool entries with matching text.
  - cutting
    - should cut inline fragment: Selecting all text in a single block and firing a cut event yields empty clipboard data (same native-behavior fallback as inline copy).
    - should cut several blocks: With two pre-existing paragraph blocks, selecting from the end of the last block up through the first (Shift+Up) and firing cut produces clipboard data with the same `text/html`, `text/plain`, and async `application/x-editor-js` JSON payload as the copy case, and afterward the editor DOM no longer contains "First block" or "Second block" text (the selected blocks were removed).
    - should cut lots of blocks: With 50 pre-existing paragraph blocks, selecting all (`{ctrl+A}` twice) and firing cut produces an `application/x-editor-js` clipboard payload whose parsed JSON array has exactly 50 entries.

## onchange.cy.ts

- onChange callback
  - should batch events when several changes happened at once: Typing "change" into a prefilled paragraph block and then pressing Enter triggers a single `onChange` invocation whose batched events are `[block-changed (index 0), block-added (index 1)]`, i.e. the text change and new-block insertion are delivered together.
  - should filter out similar events on batching: Typing "first change", waiting, then typing "second change" into the same block results in `onChange` being called exactly once, matched against a single `block-changed` event for index 0 with `target.name === 'paragraph'` — repeated changes to the same block within a batch collapse into one event.
  - should be fired with correct index on block insertion above the current (by pressing Enter at the start): Pressing Enter at the very start of the (only, empty) block fires `onChange` with a `block-added` event whose `target.name === 'paragraph'` and `index === 0`.
  - should be fired with only single "block-added" event by pressing Enter at the end of a block: Pressing Enter at the end of a prefilled paragraph's text fires `onChange` exactly once, matching a `block-added` event.
  - should be fired with correct index on block insertion after the current (by pressing enter at the end): Pressing Enter at the end of a prefilled paragraph fires `onChange` with a `block-added` event at `index === 1` (the new block after the current one).
  - should be fired on typing into block: Typing "some text" into an empty block fires `onChange` with a `block-changed` event at `index === 0`.
  - should be fired on block insertion with save inside onChange: With an `onChange` handler that itself calls `api.saver.save()`, clicking the block and using the plus-button toolbox to insert a Delimiter block fires a single batched `onChange` call containing `block-removed` (index 0, paragraph), `block-added` (index 0, delimiter), and `block-added` (index 1, paragraph) — confirming saving from within the callback doesn't break batching.
  - should be fired on block replacement for both of blocks: Converting the current paragraph block into a Header block via the plus-button toolbox fires a batched `onChange` call containing `block-removed` (index 0, paragraph) followed by `block-added` (index 0, header).
  - should be fired on tune modifying: With a prefilled Header block, opening its Block Tunes settings and clicking the 4th tune item fires `onChange` with a `block-changed` event at `index === 0`, `target.name === 'header'`.
  - should be fired when block is removed: Deleting the only (paragraph) block via Block Tunes' delete action (clicked twice to confirm) fires a batched `onChange` call with `block-removed` (index 0) followed by `block-added` (index 0), since deleting the last remaining block causes a fresh empty block to be auto-inserted.
  - should be fired when block is moved: With two paragraph blocks, clicking the last block's Block Tunes "move-up" action fires `onChange` with a `block-moved` event where `fromIndex === 1` and `toIndex === 0`.
  - should be fired if something changed inside native input: Typing into a `<textarea>` inside a Code tool block fires `onChange` with a `block-changed` event at `index === 0`.
  - should not be fired on fake cursor adding and removing: Clicking a block to open Block Tunes (which inserts a temporary "fake cursor") and then clicking away to close it (removing the fake cursor) results in `onChange` never being called (call count 0) after waiting past the mutation-observer batch timeout.
  - should be fired when the whole text inside block is removed: Backspacing the entire single-character text of a paragraph block fires `onChange` with a `block-changed` event at `index === 0`.
  - should not be fired when element with the "data-mutation-free" mark changes some attribute: For a mock tool whose root element has `dataset.mutationFree = 'true'`, programmatically setting a new attribute on that element does not trigger `onChange` at all (call count 0) after the batch timeout.
  - should not be fired when mutation happened in a child of element with the "data-mutation-free" mark: With the mutation-free root element containing a child div, setting an attribute on the *child* element also does not trigger `onChange` (call count 0), since mutation-free status propagates to descendants.
  - should not be fired when "characterData" mutation happened in a child of element with the "data-mutation-free" mark: With a contenteditable child element inside a mutation-free-marked wrapper, typing text into that child (a characterData mutation) does not trigger `onChange` (call count 0).
  - should be called on blocks.clear() with removed and added blocks: Calling `editor.blocks.clear()` on an editor with two paragraph blocks fires a batched `onChange` call containing two `block-removed` events followed by one `block-added` event (the cleared editor gets a fresh empty block).
  - should not be called on blocks.render() on non-empty editor: Calling `editor.blocks.render(...)` with new block data on an editor that already has two blocks does not fire `onChange` at all (call count 0) — `render()` bypasses the change-tracking/onChange mechanism.
  - should be called on blocks.update() with "block-changed" event: Calling `editor.blocks.update(block.id, { text: 'Updated text' })` fires `onChange` with a `block-changed` event at `index === 0` whose `target.id` equals the updated block's id.
  - should be fired when the whole text inside some descendant of the block is removed: For a custom tool whose element contains a nested contenteditable descendant with text `'a'`, clicking and clearing that nested contenteditable's content fires `onChange` with a `block-changed` event at `index === 0`.
  - should not be called when editor is initialized with readOnly mode: Creating the editor directly with `readOnly: true` and prefilled data results in `onChange` never being called (call count 0) after waiting past the batch timeout.
  - should not be called when editor is switched to/from readOnly mode: Calling `editor.readOnly.toggle(true)` and then `editor.readOnly.toggle(false)` on a normal-mode editor results in `onChange`'s call count remaining 0 after each toggle (past the batch timeout) — toggling read-only mode itself is not treated as a content change.

## sanitisation.cy.ts

- Sanitizing
  - Output should save inline formatting
    - should save initial formatting for paragraph: Initializing the editor with a paragraph block whose data text is `'<b>Bold text</b>'` and calling `editor.save()` returns that block's `data.text` unchanged as `'<b>Bold text</b>'` (allowed inline tag is preserved, not stripped).
    - should save formatting for paragraph: Typing "This text should be bold." into a block, selecting all, and clicking the inline toolbar's `[data-item-name="bold"]` button, then calling `editor.save()`, returns the block's `data.text` matching `<b>This text should be bold.(<br>)?</b>` — the applied bold formatting is preserved in saved output.
    - should save formatting for paragraph on paste: Pasting `text/html` `'<p>Text</p><p><b>Bold text</b></p>'` and calling `editor.save()` returns `blocks[1].data.text` equal to `'<b>Bold text</b>'` — inline bold formatting from pasted HTML is preserved.
  - should sanitize unwanted html on blocks merging: With two paragraph blocks, the second containing an unsanitized `<span id="taint-html">` (a tag not in the paragraph tool's sanitization config), placing the cursor at the start of the second block and pressing Backspace merges it into the first block; `editor.save()` then shows the merged block's `data.text` as `'First blockSecond XSS block'` — the merged text is sanitized and the disallowed `<span>` tag is stripped.

## api/blocks.cy.ts

- api.blocks
  - .getById()
    - should return Block API for existed id: `editor.blocks.getById(firstBlock.id)` returns a defined Block API object whose `.id` equals `firstBlock.id`.
    - should return null for not-existed id: `editor.blocks.getById('not-existed-id')` returns `null`.
  - .update()
    - should update block in DOM: after `editor.blocks.update(idToUpdate, { text: 'Updated text' })`, the rendered `div.ce-block` element's text content in the DOM becomes `'Updated text'`.
    - should update block in saved data: after calling `editor.blocks.update(...)` and waiting 100ms, `editor.save()`'s output has `blocks[0].data.text` equal to the new text.
    - should update tune data when it is provided: creating an editor with a custom `exampleTune` tune and a block whose `tunes.exampleTune` is `'citation'`, calling `editor.blocks.update(blockId, null, { exampleTune: 'test' })` (data left `null`) results in `editor.save()` output's `blocks[0].tunes` JSON-equalling `{ exampleTune: 'test' }`.
    - shouldn't update any block if not-existed id passed: calling `editor.blocks.update('wrong-id-123', { text: 'Updated text' })` rejects with an error whose `.message` is `Block with id "wrong-id-123" not found"`, and the original block's DOM text remains unchanged (`firstBlock.data.text`).
  - .insert()
    - should preserve block id if it is passed: calling `editor.blocks.insert('paragraph', { text: 'codex' }, undefined, undefined, undefined, undefined, 'test-id-123')` returns a defined Block API whose `.id` equals the explicitly passed `'test-id-123'`.
  - .insertMany()
    - should insert several blocks to passed index: `editor.blocks.insertMany([block1, block2], 0)` inserts both new blocks starting at index 0, so the resulting `.ce-block` DOM elements appear in order: "inserting block #1", "inserting block #2", then the pre-existing "first block".
  - .convert()
    - should convert a Block to another type if original Tool has "conversionConfig.export" and target Tool has "conversionConfig.import". Should return BlockAPI as well.: calling `editor.blocks.convert(existingBlock.id, 'convertableTool')` (target tool has `conversionConfig.import: 'text'`) results, after `editor.save()`, in exactly one block whose `type` is `'convertableTool'` and `data.text` matches the original text; the value returned by `convert()` itself matches a subset `{ name: 'convertableTool', id: <newBlockId> }`.
    - should throw an error if nonexisting Block id passed: calling `editor.blocks.convert('WRNG_ID', 'convertableTool')` rejects with an error whose `.message` is `Block with id "WRNG_ID" not found`.
    - should throw an error if nonexisting Tool name passed: calling `editor.blocks.convert(existingBlock.id, 'WRNG_TOOL_NAME')` rejects with an error whose `.message` is `Block Tool with type "WRNG_TOOL_NAME" not found`.
    - should throw an error if some tool does not provide "conversionConfig": converting to a registered tool (`nonConvertableTool`) that doesn't define `conversionConfig` rejects with an error whose `.message` is `Conversion from "paragraph" to "nonConvertableTool" is not possible. NonConvertableTool tool(s) should provide a "conversionConfig"`.
    - should pass tool config to the conversionConfig.import method of the tool: converting to a tool configured with `config: conversionTargetToolConfig`, whose `conversionConfig.import` returns `{ text: JSON.stringify(config) }`, results in `editor.save()` output's `blocks[0].data.text` equalling `JSON.stringify(conversionTargetToolConfig)`, proving the tool's static config object was passed into `import()`.

## api/tools.cy.ts

- Editor Tools Api
  - Toolbox
    - should render a toolbox entry for tool if configured: for a tool with a single `toolbox` entry `{ title, icon }`, clicking a block then the `.ce-toolbar__plus` button renders exactly one `.ce-popover-item[data-item-name=testTool]`, whose `.ce-popover-item__icon` HTML contains the configured icon SVG.

  - Tunes — renderSettings()
    - should contain a single block tune configured in tool's renderSettings() method: for a tool whose `renderSettings()` returns a single `TunesMenuConfig` object (`name: 'testToolTune'`), inserting the tool's block, typing text, and clicking `.ce-toolbar__settings-btn` results in `[data-item-name=testToolTune]` existing in the tunes popover.
    - should contain multiple block tunes if configured in tool's renderSettings() method: for a tool whose `renderSettings()` returns an array of two tune configs, opening block settings shows both `[data-item-name=testToolTune1]` and `[data-item-name=testToolTune2]` in the popover.
    - should contain block tunes represented as custom html if so configured in tool's renderSettings() method: for a tool whose `renderSettings()` returns a raw `HTMLElement` containing `sampleText`, opening block settings results in `.ce-popover` containing that sample text.
    - should support label alias: for tune config entries using either a `title` property or a `label` property to specify display text, opening block settings shows `[data-item-name=testToolTune1]` containing `'Test tool tune 1'` (from `title`) and `[data-item-name=testToolTune2]` containing `'Test tool tune 2'` (from `label`).
  - Paste — pasteConfig()
    - tags
      - should use corresponding tool when the array of tag names specified: for a tool with `pasteConfig.tags: ['img']`, pasting HTML `'<img>'` into a block calls the tool's `onPaste` handler (verified via spy).
      - should sanitize all attributes from tag, if only tag name specified: for `pasteConfig.tags: ['img']` (bare tag name, no sanitizer config), pasting `'<img src="foo" onerror="alert(123)"/>'` results in the `onPaste` event's `detail.data` being an `<img>` element with `attributes.length === 0` (all attributes, including `src`, stripped).
      - should sanitize all attributes from tags, even if tag names specified in uppercase: for `pasteConfig.tags: ['OL', 'LI']` (uppercase names), pasting `'<ol start="50"><li>...</li><li>...</li></ol>'` yields a pasted `<ol>` element with zero attributes and exactly 2 `<li>` children, each also with zero attributes.
      - should leave attributes if entry specified as a sanitizer config: for `pasteConfig.tags: [{ img: { src: true } }]`, pasting `'<img src="foo" onerror="alert(123)"/>'` yields a pasted `<img>` with only the `src` attribute retained (value `'foo'`) and `attributes.length === 1` (`onerror` stripped).
      - should support mixed tag names and sanitizer config: for `pasteConfig.tags: ['video', { source: { src: true } }]`, pasting `'<video width="100"><source src="movie.mp4" type="video/mp4"></video>'` yields a pasted `<video>` with zero attributes and a nested `<source>` child retaining only its `src` attribute (`'movie.mp4'`).
      - should support config with several keys as the single entry: for a single `tags` entry object `{ video: { width: true }, source: { src: true } }`, pasting the same video/source HTML yields a pasted element whose `<source>` child retains its `src` attribute value `'movie.mp4'`.
      - should correctly sanitize Table structure (test for HTMLJanitor bug): for `pasteConfig.tags: ['table', 'tbody', { td: { width: true }, tr: { height: true } }]`, pasting `'<table><tr height="50"><td width="300">Ho-Ho-Ho</td></tr></table>'` yields a pasted `<table>` whose `<tr>` retains `height="50"` and whose `<td>` retains `width="300"` (regression test for an HTMLJanitor bug mis-sanitizing nested table markup).

## inline-tools/link.cy.ts

- Inline Tool Link
  - should create a link by Enter keydown in input: creates an editor with one paragraph block, selects all its text, presses Ctrl+K to open the inline link tool, types `https://codex.so` into the inline link input and presses Enter; asserts the block now contains an `a` element with `href="https://codex.so"`.
