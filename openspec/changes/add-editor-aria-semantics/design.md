## Context

`@editorjs/ui` renders the editor shell as plain `<div>`s wired together via `EventBus` events (`ui:*:rendered`, `core:*`); see `openspec/specs/ui/spec.md`. None of `EditorjsUI`, `BlocksUI`, `ToolbarUI`, `InlineToolbarUI`, or `ToolboxUI` currently set any `role` or `aria-*` attribute. The paragraph block (`packages/tools/paragraph`) renders a bare contenteditable `<div>` with no accessible name.

The inline toolbar's popover (bold/italic/link buttons) is not rendered by `ui` directly — `InlineToolbarUI` builds a `PopoverInline` from `@editorjs/ui-kit` (external npm dependency, pinned `^1.1.5`, source is vendored into `node_modules` but not part of this workspace and not editable here). Inspecting `node_modules/@editorjs/ui-kit/src/popover/components/popover-item/popover-item-default/popover-item-default.ts`:
- Item construction (`make()`) sets no `role`/`aria-*` attributes; `params.title` only renders a visible text `<div class="title">`, and only when the popover isn't in icon-only/hint mode.
- `renderParams?.wrapperTag` can be `'button'` (falls back to `'div'`), giving native button semantics for free if the caller opts in.
- `PopoverItemDefault.getElement(): HTMLElement | null` is a **public** method returning the item's root node — so a caller can reach in and set additional attributes post-render without modifying `ui-kit` itself.

Each inline tool (`BoldInlineTool`, `ItalicInlineTool`, `LinkInlineTool`) already carries a human-readable `options.title` (e.g. `'Bold'`) via `getToolbarConfig()`, unused for accessibility today.

## Goals / Non-Goals

**Goals:**
- Every interactive control rendered by `@editorjs/ui` (toolbar plus-button, toolbox items, inline-toolbar popover items) has an accessible name and, where applicable, pressed/expanded state.
- The editable surface (blocks holder, individual blocks, paragraph's contenteditable) is identifiable and navigable by assistive tech.
- All of this is achieved without modifying `@editorjs/ui-kit` source — only via its existing public API (`render params`, `getElement()`).

**Non-Goals:**
- Full WCAG conformance audit or keyboard-navigation rework (e.g. arrow-key roving tabindex across blocks) — this change is about semantics (roles/names/state), not new interaction patterns. Keyboard nav gaps found along the way get filed as follow-ups, not fixed here.
- Changes to `@editorjs/ui-kit`'s own source/behavior. If its API can't carry a given semantic, that's documented as a limitation (see Risks), not patched upstream as part of this change.
- Localization/i18n of accessible names — names are sourced from existing English strings (tool `options.title`, etc.) as-is.

## Decisions

- **Blocks holder role**: give `BlocksUI`'s holder `role="group"` (a structural container), not `role="textbox"`. Originally planned as `role="textbox"` + `aria-multiline="true"` on the holder — but `.ejs-blocks` (the holder) is itself `contenteditable`, and so is each block inside it (confirmed in `packages/editorjs/e2e/README.md`). A bare contenteditable element gets an *implicit* `role="textbox"` per the HTML-AAM mapping regardless of what we set explicitly, so putting an explicit `role="textbox"` on the holder as well would nest one textbox inside another — an ARIA anti-pattern that can break screen reader forms-mode navigation. `role="group"` on the holder avoids that; ownership of `role="textbox"` moves to each block instead (next bullet). This is also more future-proof: once non-text block types (image, embed) exist, the holder can't honestly claim `role="textbox"` for all of them anyway.
- **Per-block wrapper vs. contenteditable element**: the block *wrapper* (`.ejs-block`/`.ejs-block__contents`) stays role-less — it's structural, not focusable. The block's actual contenteditable element (e.g. paragraph's `<div contenteditable>`) gets an explicit `role="textbox"` + `aria-multiline="true"` (content can soft-wrap across multiple visual lines) + `aria-label`. This makes explicit the role the element already implicitly carries from being contenteditable, and puts the accessible name at the level AT actually focuses — consistent with how a native `<textarea>` is labeled directly, not via its container.
- **Paragraph accessible name**: use a static `aria-label` (e.g. `"Paragraph"`) rather than `aria-labelledby` pointing at visible text, since paragraph blocks have no visible label element to point to. Placeholder/empty state (if any) uses `aria-placeholder`, mirroring the native `<textarea placeholder>` semantic AT already understands. Note this label is identical across every paragraph block in a document — it identifies the block *type*, not a unique per-instance name (see Open Questions).
- **Toolbar role**: `role="toolbar"` on `ToolbarUI`'s actions container (standard for a row of related controls), plus `aria-label="Add block"` on the plus-button, which is icon-only and would otherwise be nameless.
- **Popover-rendered surfaces (toolbox, inline toolbar items) were fixed upstream and are consumed here, not worked around.** The original plan was to apply attributes from the `@editorjs/ui` call sites — either through `ui-kit`'s render params or by reaching into rendered DOM. Investigation showed the render-params route doesn't exist for this purpose and the DOM route is unsound:
  - `InlineToolbarUI` and `ToolboxUI` never construct `PopoverItemDefault` instances. They pass plain param objects to `PopoverInline`/`PopoverDesktop`, which build items internally and expose no accessor for them. There is no `getElement()` to call per item, so the plan's step 6.3 is not reachable as written.
  - The only remaining hook is querying the popover's rendered markup (`[data-item-name]`, `.ce-popover__items`). That couples `@editorjs/ui` to another package's internal DOM, and `ui-kit` replaces item `innerHTML` wholesale on confirmation-mode toggles, so anything applied to item children is silently wiped.
  - `ui-kit` is maintained by the same team, and the information needed (`title`, `isActive`, `toggle`, `isDisabled`) is *already* passed to it as params — it simply isn't rendered as ARIA. Fixing it there is a smaller change than the workaround, and fixes every ui-kit consumer at once.

  The audit and the implementation brief were written for the `editorjs-utils` repo and live with the work they describe, not in this repo. Both were executed there and are released as `@editorjs/ui-kit` **2.0.0**, which this change consumes — see the Risks section for the publish status that gates it.
- **Source of accessible names for inline tools**: names come from the existing `InlineTool.options.title` (already `'Bold'`, `'Italic'`, etc.), which `InlineToolbarUI` already forwards to ui-kit as the item's `hint.title`. ui-kit falls back to the hint title when an item renders icon-only, which is exactly the inline toolbar's case, so no call-site change and no new field on the `InlineTool`/`BlockTool` contracts in `@editorjs/sdk` were needed. Toolbox item names likewise come from the `toolbox.title` each block tool is registered with.
- **What stays a consumer responsibility**: ui-kit can derive roles, names and states from params it already receives, but three things it cannot know:
  - The accessible *name of the container* — whether a menu is "Add block" or something else is the consumer's vocabulary. Supplied via the `messages.label` param on both popovers.
  - The relationship between the trigger and the menu — `aria-haspopup`/`aria-expanded` belong on `ToolbarUI`'s plus-button, which ui-kit never sees. Wired to the existing `ui:toolbox:opened`/`ui:toolbox:closed` events.
  - Which element holds focus while the inline toolbar is navigated. `PopoverInline` deliberately keeps DOM focus in the text (WebKit drops the selection once focus moves to a button), so it can only emit `PopoverEvent.ActiveDescendantChanged`; only the consumer knows the editable to hang `aria-activedescendant` on. `InlineToolbarUI` takes `document.activeElement` at event time and remembers it, so the attribute is removed from the very element it was set on even if focus moved on since. It qualifies that element rather than accepting whatever holds focus: a target inside the toolbar itself, or outside this editor, yields no host at all and no attributes are written — see the next bullet but one.
- **`aria-activedescendant` lands on the blocks holder, not the block.** The holder is the outermost `contenteditable`, so the browser keeps focus there and never on an individual block's editable element. Since `aria-activedescendant` is only honoured on the focused element, pointing it at the paragraph would be inert. `role="group"` supports the property, so this is valid — but it is a symptom of the nested-contenteditable structure noted in Risks, and would want revisiting if focus ever moves per-block.
- **`aria-owns` is what makes that reference resolvable.** Putting `aria-activedescendant` on the right element is necessary but not sufficient: the attribute is only resolved when it names an element *inside the focused element's subtree*, or one claimed by it via `aria-owns`. `EditorjsUI` appends the inline toolbar and the blocks holder as **siblings** under the editor wrapper (`#addInlineToolbar`/`#addBlocks`), so the popover is never inside the holder, and the reference on its own points out of the focused subtree — where assistive tech drops it entirely. `InlineToolbarUI` therefore sets `aria-owns` naming the popover on the same element, in the same call that sets the reference, and removes both together. The alternative — moving the toolbar inside the blocks holder in the DOM — was rejected: the holder is `contenteditable`, so the toolbar would become editable content and part of what the caret and the model traverse. `aria-owns` re-parents in the accessibility tree only, which is exactly the scope of the problem.

  This was a real defect, not a hypothetical: the first implementation set the reference alone. It was invisible to every layer of the test suite, because `aria.spec.ts` compared the attribute to the button's `id` (a string match that holds whether or not the reference resolves), axe never audited the navigated state, and axe does not check containment in any case. The e2e suite now asserts the resolved relationship rather than the attribute value, and audits the navigated state as a state of its own.

  With `aria-owns` in place, a real VoiceOver run (Case 8) confirms the arrangement end to end: the highlighted tool is announced by name off the reference alone. Worth noting what the defect cost in the meantime — Case 8 had been recorded as a genuinely unknowable question about screen reader behavior, when the reference was invalid on DOM structure alone and checkable in any browser with no screen reader running. An open question is worth testing for the possibility that it is a bug in disguise.

- **The reference is only ever claimed from inside this editor.** `aria-owns` and `aria-activedescendant` resolve by document-wide `getElementById`, so on a page with several editors both the popover id and the element the pair is written to have to be scoped per instance. The id is (tasks.md 10.5a); the *host* had been bounded only by the toolbar, which is not the same thing — any focused element outside the toolbar qualified, including one belonging to another editor. That is reachable today through the chromium scoping bug in tasks.md 10.5b: the toolbar raised for a selection in the second editor is the *first* editor's, which would then claim its own popover from the second editor's holder. Writing nothing is the better failure of the two — assistive technology given no reference falls back on the document, whereas one given a wrong reference confidently describes controls that operate on someone else's content.
- **A toolbar build that has been overtaken is discarded, not raced.** Building the popover awaits a `getToolbarConfig` per tool, so two selection changes can be in flight together and finish in either order. Ordering by *start* rather than by resolution is what keeps the visible toolbar tied to the current selection: each tool's `isActive` and `onActivate` close over the range its build began with, so a stale build that won the race would expose `aria-pressed` describing text the user has left, and act on that text when a button is pressed. Hiding the toolbar counts as overtaking too, so a build outstanding at dismissal cannot bring it back for a selection that no longer exists.

## Risks / Trade-offs

- **[Resolved]** `ui-kit` re-renders item content on `reset()`/confirmation-mode toggle (`popover-item-default.ts:131,206`), replacing `nodes.root.innerHTML` and wiping anything a consumer set on item children. This was originally to be mitigated by re-applying attributes on every popover rebuild. → **Resolved** by not applying consumer-side attributes at all: popover semantics move upstream (see Decisions), where they are set during `make()` and survive by construction.
- **[Resolved]** The editor's popover surfaces were inaccessible until an upstream `ui-kit` release landed. → **Resolved** by `@editorjs/ui-kit` 2.0.0, which this change consumes; the toolbox and inline toolbar are now covered by e2e alongside the blocks holder, paragraph blocks and floating toolbar.
- **[Blocking]** `@editorjs/ui-kit` 2.0.0 **is not on npm yet** — the latest published version is 1.1.5, while `packages/ui` and `packages/sdk` declare `^2.0.0`. The branch was developed against a root `resolutions` entry pointing the package at a `link:` path to a sibling `editorjs-utils` checkout; that entry and its `yarn.lock` locator have now been removed (tasks.md 5a.2), so nothing in the repo refers to anyone's local filesystem. The consequence is deliberate: `yarn install` now fails everywhere, including here, with `@editorjs/ui-kit@npm:^2.0.0: No candidates found`, and `yarn.lock` has no entry for the package at all — it cannot be written until the version exists. Publishing 2.0.0 is therefore the single remaining blocker, and the publish must include the `dist/e2e/**/*.d.ts` exclusion recorded in tasks.md 5a.1, without which consumers cannot type-check against the package. A branch that installs nowhere is a better state to review than one that installs on exactly one machine, but it does mean CI is red until the publish lands. Nothing else in this change can land ahead of it.
- **[Risk]** `@editorjs/ui-kit` 2.0.0 is a *behavioral* major: popovers now move real DOM focus, wrap radio-style item groups in a `role="group"` element, and set `hidden` on filtered-out items. Nothing in its TypeScript surface changed, so a type check will not catch a regression. → **Mitigation**: the e2e suite exercises focus movement and keyboard activation for the toolbox, and asserts the text selection survives inline-toolbar navigation, which is the interaction the focus change could plausibly break.
- **[Trade-off]** Some semantics (e.g. richer live-region announcements for collaboration cursors, or per-block landmark roles) are explicitly out of scope; this change closes the "zero ARIA" gap but doesn't claim full accessibility coverage. Flagged in Non-Goals so it isn't read as a completeness claim.
- **[Resolved]** `role="textbox"` + `aria-multiline="true"` on a `contenteditable` element (now at the per-block level, see Decisions) is a widely-used pattern (e.g. many rich text editors) but AT support/behavior varies by screen reader, and the DOM-level assertions in `aria.spec.ts` can't confirm actual AT announcement quality. → **Resolved** by adding [Guidepup](https://www.guidepup.dev/) (`@guidepup/playwright`), which drives a real VoiceOver instance against Safari and exposes what it actually spoke as assertable strings — `e2e/tests/voiceover.spec.ts` covers all 18 cases in `voiceover-verification.md`, all asserting and all passing — there is no manual checklist left. Case 8 (arrow-key navigation via `aria-activedescendant`) was the last one open and is now **settled positively**: VoiceOver announces each highlighted tool by name off the reference alone ("Bold toggle button", then "Italic toggle button"), with DOM focus never leaving the text and the selection intact. It was brought in as a *measurement* first — asserting only what was already established and printing VoiceOver's output — so that its expected value came from observation rather than from a guess about screen reader behavior. Guidepup can't run headless or in CI (screen readers are singletons and need a real, headed session), so this is a separate, local-only suite (`playwright.voiceover.config.ts`, `yarn test:e2e:voiceover`) — it doesn't change the fact that this repo's e2e suite as a whole isn't wired into CI yet. Alongside it, `@axe-core/playwright` covers the complementary structural side (missing names, invalid roles, contrast) in `e2e/tests/axe.spec.ts`, cheap to run and does run under the existing chromium/webkit projects.
- **[Risk]** Nested contenteditable regions: `.ejs-blocks` (the holder) and each block's contenteditable child are both native `contenteditable` elements, which HTML-AAM implicitly maps to `role="textbox"` regardless of any explicit role we set. An earlier draft of this design put `role="textbox"` on the holder, which would have produced a textbox nested inside a textbox — invalid ARIA, likely to confuse screen reader forms-mode navigation. → **Resolved** by moving `role="textbox"` ownership to each block and giving the holder `role="group"` instead (see Decisions). Flagged here since it's the kind of DOM-implicit-role interaction that's easy to reintroduce accidentally as new block types (also contenteditable) are added.

## Migration Plan

Purely additive DOM attribute changes — no data migration, no API version bump. Roll out as a single change; if a regression is found (e.g. a screen reader misbehaves with `role="textbox"` on the blocks holder), revert is a simple attribute removal with no state to unwind.

## Open Questions

- ~~Does `@editorjs/ui-kit`'s `PopoverInline`/`PopoverItemDefault` support `wrapperTag: 'button'` end-to-end today?~~ **Resolved by source inspection of the installed 1.1.5, no spike needed.** `PopoverInline`'s constructor (`popover-inline.ts:18-34`) *already* hardcodes `wrapperTag: 'button'` for `PopoverItemType.Default`, with a comment explaining it fixes a Safari focus-loss bug. Inline toolbar items are therefore already native `<button type="button">`. It also accepts only `(params: PopoverParams)` — no second `itemsRenderParams` argument — so passing render params from the call site is both impossible and unnecessary. `PopoverDesktop` (used by the toolbox) does accept the second argument but does not opt in, so toolbox items are still `<div>`s; that is covered in §1 of the upstream audit.
- ~~Should toolbox items use `role="menuitem"` or `role="option"`?~~ **Resolved upstream**: ui-kit 2.0.0 derives `menuitem` (or `menuitemradio`/`menuitemcheckbox` when the item has a `toggle` param), and pairs it with a roving-tabindex focus model rather than `aria-activedescendant`. `option` remains available via the new `role` item param if a listbox-shaped consumer ever needs it.
- `aria-label="Paragraph"` is identical across every paragraph block in a document — does that meaningfully help an AT user navigate between blocks, or just repeat "Paragraph, edit text" on every Tab/arrow move with no distinguishing information? Not blocking for this change since there's currently only one block type, but worth revisiting (e.g. via `aria-posinset`/`aria-setsize` on the wrapper, or richer per-instance context) before more block types land and per-block identity starts to matter more.
