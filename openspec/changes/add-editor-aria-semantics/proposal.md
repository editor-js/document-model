## Why

`@editorjs/ui` (the default rendering shell) and `packages/tools/paragraph` currently emit zero `aria-*` attributes or `role`s anywhere — confirmed by grepping `packages/ui/src`, `packages/tools/paragraph/src`, and the compiled `@editorjs/ui-kit` output. The editor is a contenteditable-based block editor with a floating toolbar, an inline formatting popover, and a toolbox, none of which expose any accessible name, role, or state. As a result the editor is effectively unusable with a screen reader today. This was surfaced while writing Playwright e2e tests for `packages/editorjs` (`packages/editorjs/e2e/README.md`), where the lack of ARIA semantics also meant tests had to fall back to CSS-class selectors instead of `getByRole`/`getByLabel`.

## What Changes

- Add a `role="group"` structural role to the blocks holder (`BlocksUI`), and `role="textbox"` + `aria-multiline="true"` + an accessible name to each block's contenteditable element (starting with the paragraph tool), so assistive tech announces the editor as a set of editable text regions and lets a user navigate between blocks.
- Add an accessible name to the paragraph tool's contenteditable element (`packages/tools/paragraph`) via `aria-label`, plus `aria-placeholder` from the tool's configured `placeholder`, so the block's purpose and empty state are both announced — a contenteditable has no native `placeholder`, so an empty block would otherwise reach assistive tech as an unlabelled empty field.
- Add `role="toolbar"` to `ToolbarUI`'s actions container and an accessible name to its plus-button, so the floating toolbar's controls are operable and announced. `ToolbarUI` also focuses the plus-button when it opens the toolbox, so that dismissing the toolbox returns focus there rather than dropping it (see the Safari bug under Impact).
- **Popover-rendered surfaces get their semantics from `@editorjs/ui-kit`, which this change consumes.** The toolbox (`ToolboxUI`) and the inline toolbar's items (`InlineToolbarUI`) are both rendered by ui-kit, which used to emit zero `role`/`aria-*` and expose no ARIA params. Rather than reaching into its rendered DOM from here — fragile (ui-kit replaces item `innerHTML` on confirmation-mode toggles) and coupling `@editorjs/ui` to another package's internal markup — the semantics were implemented upstream (the audit and the implementation brief live in the `editorjs-utils` repo alongside the work they describe). `@editorjs/ui-kit` **2.0.0** now derives `menu`/`menuitem`/`button` roles, accessible names, `aria-pressed`/`aria-checked` and a real roving-tabindex focus model from params the editor already passes it.
- Consume that release: bump `@editorjs/ui-kit` to `^2.0.0` and wire up the parts only the consumer can supply — an accessible name for the toolbox menu and for the inline toolbar (`messages.label`), `aria-haspopup`/`aria-expanded` on the plus-button that controls the toolbox, and `aria-activedescendant` mirroring for the inline toolbar, which deliberately never takes DOM focus so the text selection survives — paired with `aria-owns`, without which the reference names an element outside the focused subtree and assistive tech ignores it (see design.md).
- No changes to the OT/collaboration protocol, the model, or any public `@editorjs/sdk` tool-authoring contracts — this is additive DOM/attribute work in the rendering layer.

## Capabilities

### New Capabilities
(none — this change adds requirements to existing capabilities, it doesn't introduce a new one)

### Modified Capabilities
- `ui`: `BlocksUI` and `ToolbarUI` gain requirements to render accessible roles and names on their DOM output. `ToolboxUI` and `InlineToolbarUI` gain requirements to name the menu/toolbar their popovers render, and `InlineToolbarUI` additionally to mirror the keyboard-highlighted item onto `aria-activedescendant`.
- `tools`: `Paragraph` gains a requirement to expose an accessible name on its contenteditable element.

## Impact

- Affected code: `packages/ui/src/Blocks/Blocks.ts`, `packages/ui/src/Toolbar/Toolbar.ts`, `packages/ui/src/Toolbox/Toolbox.ts`, `packages/ui/src/InlineToolbar/InlineToolbar.ts`, `packages/tools/paragraph/src/index.ts`. Additive attributes plus the `aria-activedescendant` wiring and the plus-button focus move.
- Dependency bump: `@editorjs/ui-kit` `^1.1.5` → `^2.0.0` in `packages/ui` and `packages/sdk`. The major is behavioral, not a type-surface break — real focus movement inside popovers, a `role="group"` wrapper around radio-style item groups, and a `hidden` attribute on filtered-out items.
- **Blocked on publishing that dependency.** 2.0.0 is not on npm (1.1.5 is the latest). The `resolutions` entry that linked `@editorjs/ui-kit` to a local `editorjs-utils` checkout during development has been removed, along with its `yarn.lock` locator, so the branch no longer installs anywhere — `yarn install` fails with `No candidates found` and CI is red until the publish lands. That is intentional: a branch that installs on exactly one machine is harder to review than one that plainly does not install yet. See the first Risks entry in design.md.
- Bug fixed along the way: `InlineToolbarUI` appended a fresh popover element per render without removing the previous one, so two overlapping selection changes left an orphaned popover in the DOM. It now removes the previous popover element and appends the new one, keeping exactly one — otherwise the same tool buttons could surface twice in the accessibility tree.
- Bug found by the focus-destination tests (D in the case list below): in Safari, dismissing the toolbox dropped DOM focus onto `<body>`, so a keyboard or screen-reader user lost their place in the editor entirely — on Escape and after inserting a block alike. Safari does not focus a `<button>` when it is clicked, so the popover captured `document.body` as the element to restore focus to when it closed. `ToolbarUI` now focuses the plus-button as it opens the toolbox, which both fixes the restore and matches the WAI-ARIA menu button pattern. Chromium was unaffected, which is why only the webkit e2e target caught it.
- Bug introduced by this change and caught by the VoiceOver suite: the roving tabindex added to the block actions toolbar handled `ArrowLeft`/`ArrowRight` with any modifiers held and called `preventDefault()` on them — but VoiceOver moves its cursor with VO+Right and VO+Left, which reach the page as `Control`+`Option`+arrow. Since Safari focuses a control when the VoiceOver cursor lands on it, a user whose cursor reached the plus button could not move off it again. `ToolbarUI` now ignores modified arrows entirely. The accessibility tree was correct the whole time and the keyboard was not, which is a distinction only a real screen-reader run makes — seven of the seventeen VoiceOver cases failed on it simultaneously, having passed 16 of 17 on the same code the run before.
- Known gap, recorded rather than fixed here: no UI plugin's `destroy()` is ever called. Each of `InlineToolbarUI`, `ToolbarUI` and `ToolboxUI` declares one, but `Core` and `EditorJS` expose no `destroy()` and nothing invokes them, so the teardown this change corrected — hiding before detaching the holder, cancelling the pending announcement, dropping the popover's document-level listeners — is currently unreachable. It is correct and it becomes load-bearing as soon as an editor can be unmounted. Giving the editor a lifecycle is its own change; tasks.md 10.8.
- Known gap, recorded rather than fixed here: inserting a block from the toolbox returns focus to the plus-button rather than putting the caret in the block that was just inserted. That is the pre-existing `focus: true` `@todo` in `ToolboxUI#addTool`; the tests assert only that focus is not lost.
- Hardening noticed while automating Case 7: the first version of that fix used `holder.replaceChildren(popover, liveRegion)`, which detached and re-inserted the live region on every render — immediately before announcing into it. A live region should already be in the accessibility tree when its text changes, or assistive tech may not treat the change as an update at all. Only the popover is swapped now, leaving the region mounted from construction. This was not observed failing against VoiceOver — it's a fix on ARIA-practice grounds.
- Test impact: verified by Playwright e2e in `packages/editorjs/e2e` rather than unit tests — neither `@editorjs/ui` nor `@editorjs/paragraph` has any test infrastructure today (no jest config, no `test` script, no specs), and the real browser accessibility tree is a stronger check for ARIA than a jsdom approximation would be. `e2e/tests/aria.spec.ts` covers all four surfaces; `editor.spec.ts` is fully migrated to `getByRole`. The fixture mounts one paragraph per `text` search param, so cases that need a multi-block or an empty document remount with e.g. `?text=Alpha&text=Beta`; with no param it stays the single `Hello world` block every earlier test was written against.
- Test tooling added: `@axe-core/playwright` for static WCAG-rule audits (`e2e/tests/axe.spec.ts`, runs alongside the rest of `test:e2e`) and `@guidepup/playwright`/`@guidepup/guidepup` to drive a real VoiceOver instance and assert on what it actually announces (`e2e/tests/voiceover.spec.ts`, its own `playwright.voiceover.config.ts` and `yarn test:e2e:voiceover` script — macOS-only, headed, not part of `test:e2e` or CI). Together they bring the whole `voiceover-verification.md` checklist under `yarn test:e2e:voiceover` — all 18 cases automated, run and passing, with nothing left manual. Case 8 settled the change's longest-open question positively: VoiceOver does follow `aria-activedescendant` set on the contenteditable `role="group"` holder, announcing each highlighted tool by name with the text selection intact. Two cases failed with more than one available explanation, and only some of them were this change's fault; each was settled by a scratch page varying one attribute at a time rather than by reasoning about what a screen reader probably does, and both findings contradicted the obvious first guess: `aria-controls` turned out to be irrelevant to the plus-button's unannounced `aria-expanded` (`aria-haspopup` suppresses it), and the `role="textbox"` added by this change turned out not to be why links inside a block go unannounced (`contenteditable` is, as a plain one behaves identically). The scratch pages were throwaway; the results are recorded under Cases 15 and 17 of `voiceover-verification.md`.
- No breaking changes to this repo's public APIs.
