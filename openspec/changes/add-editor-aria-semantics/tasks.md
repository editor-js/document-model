## 10. Lifecycle, keyboard and string-handling cleanups

Follow-ups from the same review pass, none of them user-visible today but each one a contract
the code was not keeping.

- [x] 10.1 Stop `InlineToolbarUI` holding a destroyed popover. `#hide()` destroyed the instance but left `#popover` set, so the next rebuild destroyed it again — re-running item cleanup and re-emitting `PopoverEvent.Closed` to any future listener. Extracted `#destroyPopover()`, which clears the reference, the popover element and the `aria-activedescendant`/`aria-owns` pair together, and is now the single teardown path for hide, rebuild and plugin destroy alike. `destroy()` previously removed the holder while leaving the popover's document-level listeners and any pending announcement alive; it tears down properly first now
- [x] 10.1a Tear the old popover down *after* the last `await` in `#renderPopover` rather than on entry. Task 5.10 fixed the orphaned *element* left by two overlapping selection changes, but not the orphaned *instance*: with teardown on entry, the second call disposes before the first has built anything, so the first call's popover is then overwritten with its document-level listeners still attached. Disposing immediately before building means each call disposes whatever is actually current, whichever order they interleave in — and the outgoing toolbar no longer blinks out for the duration of the await
- [x] 10.1b Decide *which* render wins, not just that each one disposes correctly. 10.1a made two interleaved `#renderPopover` calls tear down safely in either order, but left the outcome to whichever resolved last — and with an awaited `getToolbarConfig` per tool, that need not be the later selection. The loser is not a redundant rebuild: `isActive`/`onActivate` close over the `textRange` the call started from, so a late-resolving older build puts up buttons whose `aria-pressed` describes text the user has moved off and which act on it when activated. A generation counter is now claimed before the first await and rechecked after the last; a superseded build returns without tearing anything down or building anything, and `#handleSelectionChange` skips the `#move()`/`#show()` that would otherwise reposition and re-announce the toolbar the winner put up. `#hide()` bumps the same counter, so a build outstanding at dismissal can no longer resurrect the toolbar for a selection that is gone. Specified in `specs/ui/spec.md`. **Not covered by a test**: landing inside the window needs two selection changes to interleave with a controlled resolution order, which no Playwright interaction arranges deterministically — same disposition as 10.3 and 10.7
- [x] 10.1c Unsubscribe `InlineToolbarUI` from the core's selection changes in `destroy()`. 10.1 gave the method a comment about tearing down "properly", but the constructor's `core:selection-changed` subscription outlived it — and as an inline arrow it could not have been removed at all. Held as a field now and removed first, before the popover teardown, so a selection change arriving mid-teardown cannot put a new popover into the holder that is about to be detached. Still dead code until 10.8 gives the editor a lifecycle; the point is that the method now does what it says
- [x] 10.2 Move the popover element out of the `#nodes` bag into its own nullable field. `#nodes` is for the parts built once in `#render`; the popover element is replaced on every rebuild and absent while hidden, and typing it as always-present is what let the stale reference in 10.1 go unnoticed
- [x] 10.3 Make the live-region announcement cancellable. It was scheduled through `delay()`, which returns no handle, so a toolbar dismissed inside the 50ms window still announced itself as available. Now a tracked `setTimeout`, cancelled on hide, on destroy, and before scheduling a replacement. **Not covered by a test**: the race is a 50ms window that no deterministic Playwright interaction can reliably land inside, and a timing-dependent assertion here would pass for the wrong reason more often than it would catch anything. Specified in `specs/ui/spec.md` instead
- [x] 10.4 Give the block actions toolbar the roving tabindex its `role="toolbar"` promises — one control in the tab order, horizontal arrow keys moving between them, `aria-orientation` declared. Scoped to the container's own direct-child buttons, so keys arriving from the toolbox popover rendered inside it stay the popover's to handle. Invisible at runtime with one control, which is the point: adding a second one no longer silently makes the role a lie. Asserted structurally in `aria.spec.ts` — a behavioural assertion would be vacuous at a single control
- [x] 10.4a **Stop the roving tabindex swallowing VoiceOver's own navigation keys — a real accessibility bug introduced by 10.4 and caught by the VoiceOver suite.** `#handleActionsKeydown` matched `ArrowLeft`/`ArrowRight` regardless of modifiers and called `preventDefault()`, but **VO+Right and VO+Left reach the page as `Control`+`Option`+arrow**. Safari focuses a control when the VoiceOver cursor lands on it, so once a user's cursor reached the plus button the editor ate every attempt to move off it: the cursor was trapped on the button for the rest of the session. It now ignores any modified arrow — those belong to the screen reader, the OS (`Meta`) or selection (`Shift`) — and handles the unmodified ones only. Seven of the seventeen VoiceOver cases failed on this at once (1, 2, 7, 11, 12, 13, 15) with three different-looking symptoms, and it presented as harness flakiness: it only bites once the cursor has reached a toolbar control, so an earlier full run passed 16 of 17 on the same code, and the accessibility *tree* was correct throughout — the defect was in the keyboard, which no attribute assertion can see. Settled without a screen reader: Playwright's failure snapshot marked the plus button `[active]`, a headless mount proved focus is on `<body>` there, and a scratch spec pressing `Control+Alt+ArrowRight` at the focused button reported `defaultPrevented: true`. Regression test in `aria.spec.ts` ("leaves modified arrow keys to their real owner") asserts the whole swallowed-key list rather than four separate negatives, so a handler that stops preventing the plain arrow too fails instead of passing vacuously. New scenario in `specs/ui/spec.md`. **Confirmed: the full VoiceOver suite is green after the fix** — all seven cases recovered together, which a harness-flakiness explanation would not have produced
- [x] 10.5 Collect the strings `@editorjs/ui` writes into the DOM in `packages/ui/src/messages.ts`, and name the paragraph tool's in its own module. i18n stays out of scope; this is only the seam it would attach to, so that sourcing these from config later is a change to one file per package rather than to every call site
- [x] 10.5a Make the inline toolbar's popover id per instance rather than a single constant. `aria-owns` resolves by document-wide `getElementById`, so a fixed id on a page with two editors hands the second editor's blocks holder the *first* editor's popover — pointing assistive tech at controls that operate on a different document. Introduced by 9.1 and caught only by mounting two editors; the fixture grew an `?editors=2` mode for it
- [ ] 10.5b **Pre-existing bug found by that fixture, not this change's to fix: on chromium the inline toolbar is not scoped to its editor instance.** Two editors mount two toolbars, but selecting text in the second raises the *first* one's — positioned over the first editor and operating on its selection. Confirmed by locating the popover that appears: it is inside editor 0's wrapper whichever editor was clicked. Webkit raises the correct one, so the selection pipeline is leaning on engine behaviour somewhere. Pinned per engine with `test.fail(browserName === 'chromium')` in `aria.spec.ts`, so fixing chromium trips the test rather than leaving it asserting the bug. Worth its own change
- [x] 10.7 Make `InlineToolbarUI#setActiveDescendant` total in which element it writes to. It picked up `document.activeElement` only when that was an `HTMLElement` and otherwise fell through to *whatever host it used last*, writing `aria-owns`/`aria-activedescendant` onto a previously focused element that had nothing to do with the current popover; and it adopted a new host without releasing the old one, so two different elements could hold the pair at once. Host selection is now a single `#activeDescendantTarget()` returning the element or null, the previous host is released before a new one is adopted, and a focus that is *inside the toolbar itself* yields null rather than a host — a control there claiming the popover would make an element own its own ancestor, and the reference is inert anyway, since the focused button is the active item. **Not covered by a test, deliberately.** A test was written for the Tab-into-the-toolbar case and passed against the unfixed code: ui-kit only emits `ActiveDescendantChanged` for its virtual-cursor navigation, and Tab switches it to real focus, so the two states are mutually exclusive upstream and neither branch is reachable from the editor today. Both are guards against an upstream behaviour change, and a test that cannot fail is worse than none — the same disposition as 10.3, and the rule this suite's own README states. The full VoiceOver suite was re-run green afterwards, which is what confirms the rework did not disturb the `aria-activedescendant` path Case 8 depends on
- [x] 10.7a Bound `#activeDescendantTarget()` to the editor the toolbar belongs to. 10.7 made host selection total, but bounded it only by the *toolbar*: any focused element outside the toolbar qualified, including one in another editor. That is reachable today through 10.5b — on chromium, selecting in the second editor raises the *first* editor's toolbar, which then claimed its own popover from the second editor's holder, pointing assistive technology at controls that operate on a different document. The guard does not fix the scoping bug; it downgrades a confidently wrong claim to no claim, which is the safer failure for a screen reader user. Note it also changes how 10.5b's `test.fail()` case fails on chromium — a missing `aria-owns` rather than a cross-editor one — which the test's comment now records so the eventual fixer isn't misled
- [ ] 10.7b **Not this change's to fix — a rejected toolbar build is discarded silently.** `#onSelectionChanged` fires `#handleSelectionChange` as `void`, so a tool throwing from `getToolbarConfig` rejects the whole `Promise.all` and the rejection goes nowhere: no toolbar, no formatting controls, nothing logged. Pre-existing, but 10.1b changes what it costs — an older build that would once have completed and put *something* up now bails on the generation check, so a failing newest build is the entire outcome. Left as a `@todo` on `#onSelectionChanged` rather than fixed here, because choosing between hiding the toolbar, retrying, and rendering the tools that did resolve is a decision about tool-failure semantics across the editor, and this change has no standing to make it for every surface that awaits tool code. Worth its own change, together with whatever the toolbox should do when a tool's `toolbox` config throws
- [ ] 10.8 **Not this change's to fix, and not currently reachable: no UI plugin's `destroy()` is ever called.** `InlineToolbarUI`, `ToolbarUI` and `ToolboxUI` all declare one, but `Core` and `EditorJS` expose no `destroy()` and nothing invokes the plugins' — the only `.destroy()` call in the whole source tree is the popover's, inside `InlineToolbarUI` itself.
